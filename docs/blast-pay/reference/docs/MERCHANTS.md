# Мерчанты и промоакции

Что изменилось, когда в каталоге появились первые настоящие заведения —
KAFFEINE и ZAYTUN — и куда делись пятнадцать выдуманных.

Ветка: `feature/kaffeine-zaytun-real-data`.

---

## 1. Словарь: merchants ≠ новая таблица

Задача пришла в терминах `merchants`, `menu_categories`, `menu_items`,
`promotions`, `promotion_redemptions`. В базе те же сущности жили с первой
недели проекта под другими именами:

| Из задачи | В базе | Почему не переименовали |
|---|---|---|
| `merchants` | `venues` | 87 миграций, весь каталог, активация, визиты, споры и биллинг ссылаются на `venue_id` |
| `menu_categories` | `venue_menu_sections` | — |
| `menu_items` | `venue_menu_items` | — |
| `promotions` | `offers` | `offer_id` в активациях, визитах, пулах купонов, напоминаниях |
| `promotion_redemptions` | `activations` (+ `visits`) | активация обещает скидку, визит фиксирует деньги |

Заводить рядом вторые таблицы с требуемыми именами означало бы две модели
одних и тех же заведений — и два разных ответа на вопрос «открыт ли
ресторан». Поэтому хранение осталось прежним, а имена из задачи заведены
как **view** поверх него: `public.merchants`, `public.menu_categories`,
`public.menu_items`, `public.promotions`, `public.promotion_redemptions`.

View только на чтение. Пишут через RPC (`merchant_*`, `admin_*`), потому
что запись мимо проверок прав и лимитов — ровно то, чего здесь быть не
должно.

`merchants` отдаёт то, что задача просила плоскими полями, а в базе лежит
иначе: `latitude`/`longitude` разбираются из PostGIS-точки `location`,
`working_hours` собирается из `venue_hours`, `is_active` считается из
`status` и `deleted_at`. То же у `promotions`: `days_of_week`,
`start_time`, `end_time` собираются из `offer_slots`.

## 2. Новые колонки

### `venues`

| Колонка | Зачем |
|---|---|
| `merchant_type` | enum `coffee_shop / cafe / restaurant / bakery / bar / fast_food / other`. Не то же, что `category_id`: категория — раздел витрины для гостя, тип — природа бизнеса для админки |
| `email` | письма о выплатах, восстановление доступа в дашборд. Есть проверка формы |
| `logo_path` | путь в бакете `catalog-assets`. Не то же, что обложка `cover_photo_id`: обложка широкая, логотип квадратный |
| `google_place_id`, `google_maps_url` | откуда взяты координаты и часы. Когда заведение переедет, будет видно, что старая точка была не выдумана |

### `offers`

| Колонка | Зачем |
|---|---|
| `description` | у акции был только заголовок и условия |
| `buy_quantity`, `get_quantity` | «два по цене одного» |
| `reward_item_id` → `venue_menu_items` | что именно достаётся бесплатно. Ссылка, а не текст: иначе подарок нельзя сверить с чеком |
| `cashback_percent` | кэшбэк |
| `daily_limit`, `total_limit` | потолок активаций за сутки и за всё время |
| `cooldown_hours` | пауза между активациями одного гостя |

### `venue_menu_items`

| Колонка | Зачем |
|---|---|
| `is_available` | «сегодня нет лосося» — не удаление позиции: завтра он будет, а удалённая строка утащит `reward_item_id` у акции |
| `updated_at` | дашборду нужно знать, когда меняли цену |

## 3. Типы акций

`offer_kind` было `percent | fixed | special`. Стало плюс `buy_x_get_y`,
`free_item`, `cashback`, `combo`. `special` оставлен: на нём висят ранее
заведённые офферы, и переписывать их задним числом значит соврать про то,
чем они были.

Шесть типов из задачи закрыты так:

| Задача | `offer_kind` | Обязательные поля |
|---|---|---|
| Percentage discount | `percent` | `discount_percent` |
| Fixed discount | `fixed` | `discount_fixed` |
| Buy X Get Y | `buy_x_get_y` | `buy_quantity`, `get_quantity` |
| Free item | `free_item` | — (`reward_item_id`, когда придёт меню) |
| Cashback | `cashback` | `cashback_percent` |
| Combo offer | `combo` | — |

Проверяет это `offers_kind_shape`. Старое ограничение
`offers_kind_consistent` перечисляло разрешённые типы поимённо и не
пускало ни один новый — снято, его смысл (процент и фиксированная сумма
не уживаются в одной акции) переехал в `offers_kind_shape`. Теперь новый
тип требует правки в одном месте, а не в двух.

## 4. Лимиты: `check_promotion_limits`

До этой ветки `per_user_limit`, `per_user_period` и (ещё не существовавший)
cooldown были декларацией: колонки заполнялись, показывались в админке и
**не читались ни одной функцией**. Заведение, поставившее «раз в неделю»,
получало «раз в день» — столько, сколько умел `per_user_daily`.

```sql
select public.check_promotion_limits(p_offer, p_user, p_at);
```

Проверяет по порядку и возвращает первую причину отказа:

| Код | Когда |
|---|---|
| `OFFER_UNAVAILABLE` | акции нет или удалена |
| `PROMO_NOT_ACTIVE` | черновик, на модерации, снята |
| `VENUE_PAUSED` | заведение не опубликовано |
| `PROMO_NOT_STARTED` | `starts_at` в будущем |
| `PROMO_EXPIRED` | `ends_at` прошёл |
| `PROMO_WRONG_DAY` | сегодня не тот день (`offer_slots.weekday`) |
| `PROMO_OUTSIDE_HOURS` | сейчас не то время (`offer_slots`, окна через полночь учтены) |
| `PROMO_TOTAL_LIMIT` | исчерпан `total_limit` |
| `PROMO_DAILY_LIMIT` | исчерпан `daily_limit` за сутки заведения |
| `PROMO_USER_LIMIT` | гость выбрал `per_user_limit` за `per_user_period` |
| `PROMO_COOLDOWN` | не прошёл `cooldown_hours` |

Ответ содержит не только «нельзя», но и когда станет можно: `next_at`,
`wait_seconds`, `windows`. Экран «ещё три часа» и экран «акция кончилась»
ведут гостя к разным действиям, и одним кодом их не развести.

Считаются активации в статусе `active` и `redeemed`. Просроченная и
отменённая не считаются — гость до скидки не дошёл, и сжигать ему лимит
за это нечестно.

Сутки — по часовому поясу города заведения, а не сервера: «50 чашек в
день» в Душанбе обнуляется в душанбинскую полночь.

### Количество и бронь

`daily_limit` и `coupon_pools` — разные механизмы, но одно число.

Колонка — счётчик активаций, пул умеет держать бронь под гостя. Пока они
жили отдельно, экран акции читал пустой пул и писал «Осталось купонов:
Без ограничения» на акции с лимитом 25 в сутки, а кнопки брони не
показывал: количество у акции было, а гость про него не знал и занять
место не мог.

Поэтому у каждой акции с `daily_limit` есть производный пул
(`coupon_pools.from_daily_limit = true`), и триггер `offers_sync_pool`
держит его `quantity` равным лимиту: правка лимита едет в пул, снятый
лимит гасит пул, возвращённый — поднимает. Пулы, заведённые руками, этот
флаг не ставят, и триггер их не трогает — там можно держать своё число
и свой `period` (`week`/`month`/`total`).

Действуют по-прежнему оба, срабатывает тот, что строже: пул отказывает
на брони (`NO_COUPONS_LEFT`), колонка — на активации
(`PROMO_DAILY_LIMIT`).

Вызывается из `activate_offer` сразу после `is_offer_live`. Старый
`is_offer_live` оставлен: он отвечает грубым `OFFER_NOT_LIVE`, который
приложение уже показывает, и его же зовёт каталог.

### Чего в модели нет: доступ и приоритет

Каталоги Rudaki House и Anzur (по 15 предложений) на две трети состоят из
механик, которых в `offer_kind` нет: «стол, который держат», «выбор
стола», «билеты раньше всех», «ночная карта», «свой менеджер брони»,
«меню до публикации». Это не скидка и не подарок — это доступ и
приоритет, и цена их для заведения нулевая.

Заводить их как `special` нельзя: гость нажмёт «Взять акцию», получит код
и не получит ничего похожего на обещанное. Поэтому в базу они не попали —
из каждого каталога взято по шесть предложений, которые модель выражает
(`free_item`, `combo`, `special` как разовое событие).

Второе, чего не хватает: почти все эти предложения адресованы уровню
статуса (Silver / Gold / Black / Member), а у гостя в базе статус один —
`basic`. Пока уровней нет, «для Gold и выше» выразить нечем.

## 5. Дашборд мерчанта

Все функции — `SECURITY DEFINER` с явной проверкой
`is_member(venue, 'manager')`.

| Функция | Что делает |
|---|---|
| `merchant_update_profile(venue, patch)` | имя, описание, адрес, телефон, почта, инстаграм, логотип, средний чек, тип |
| `merchant_set_hours(venue, hours)` | расписание целиком (выходной — отсутствие строки) |
| `merchant_save_menu_category(...)` | создать/изменить раздел меню |
| `merchant_delete_menu_category(id)` | удалить пустой раздел |
| `merchant_save_menu_item(...)` | позиция: название, цена, наличие, «входит в акцию» |
| `merchant_delete_menu_item(id)` | удалить, если не подарок в живой акции |
| `merchant_save_promotion(venue, id, patch)` | создать/изменить акцию |
| `merchant_set_promotion_status(id, status)` | отправить на проверку, снять, вернуть, убрать |
| `merchant_delete_promotion(id)` | мягкое удаление |
| `merchant_promotions(venue)` | список со счётчиками погашений |

**Правка живой акции.** Косметика (описание, условия, includes/excludes) и
лимиты правятся на ходу. Всё, что меняет саму сделку — тип, проценты,
суммы, подарок, даты, расписание — возвращает акцию в `draft` и требует
повторного одобрения. Ответ говорит об этом полем `sent_back_to_draft`.
Лимиты отнесены к ёмкости заведения, а не к обещанию гостю, поэтому
правятся без повторной модерации.

**Переходы статуса, доступные мерчанту:**

```
draft ──────► moderation      отправить на проверку
moderation ─► draft           отозвать
active ─────► paused          снять с публикации
paused ─────► active          вернуть уже одобренную
любой ──────► archived        убрать совсем
```

`draft → active` отсутствует намеренно: иначе модерацию можно обойти,
просто не нажимая «отправить».

## 6. Админка

Уже существовали (заведены из репозитория внутренней админки, см. §9):
`admin_venues_list`, `admin_venue_detail`, `admin_set_venue_status`,
`admin_offers_list`, `admin_offer_detail`, `admin_set_offer_status`.

Добавлены:

| Функция | Что делает |
|---|---|
| `admin_create_merchant(slug, name, category, lat, lng, address, patch)` | завести заведение. Всегда в `draft` |
| `admin_update_merchant(venue, patch)` | правка данных: имя, адрес, координаты, категория, район, контакты, радиус геозоны |
| `admin_set_merchant_member(venue, email, role)` | выдать владельцу доступ в дашборд |
| `admin_review_promotion(id, approve, reason)` | одобрить (`→ active`) или отказать (`→ draft`) с причиной |

`admin_set_merchant_member` важнее, чем кажется: без строки в
`venue_members` ни одна функция `merchant_*` не пропустит владельца, и
дашборд у него пуст. Аккаунт должен существовать — сначала владелец
заходит в приложение, потом получает права.

Рейтинг (`rating_avg`, `rating_count`) отсюда не правится: он считается из
отзывов через `recalc_venue_rating`. Ручная правка рейтинга — ровно тот
случай, когда цифра в приложении перестаёт что-то значить.

Отказ возвращает акцию в черновик, а не в архив: заведению нужно
поправить и прислать снова.

## 7. RLS

**Починена дыра.** Политики `venue_menu_sections_read` и
`venue_menu_items_read` стояли как `using (true)` — меню читалось у любого
заведения, включая снятое с публикации и черновое. Пока всё было
опубликовано, это не проявлялось; KAFFEINE и ZAYTUN заводятся в `draft`,
и их меню до одобрения видеть никто не должен.

Политики чтения меню разделены по ролям. Одна политика с веткой
`is_member(...) or is_admin()` для анонима падала:

```
ERROR: 42501 permission denied for function is_member
```

Право на выполнение `is_member`/`is_admin` у `anon` отобрано намеренно
(`20260828234500_revoke_anon_execute`), а Postgres проверяет право на
функцию до того, как выяснится, что первая половина `OR` уже дала `true` —
короткого замыкания здесь нет. Поэтому политик две: анонимная не зовёт
эти функции вовсе.

Итог:

| Кто | Заведения | Акции | Меню |
|---|---|---|---|
| `anon` | только `active` | только `active` | только у `active`, только `is_available` |
| гость | то же | то же + персональные | то же |
| персонал заведения | своё в любом статусе | своё | своё целиком, включая скрытые позиции |
| менеджер | + запись | + запись | + запись |
| админ | всё | всё | всё |

Добавлены политики записи для мерчанта на `venue_hours`, `venue_photos`,
`offer_slots`, `coupon_pools`, `venue_menu_*`; `venues` INSERT — только
админ (иначе любой вошедший гость может создать «заведение» и стать его
владельцем); `venue_members` — владелец заведения и админ.

## 8. Данные

### Убрано

Пятнадцать выдуманных заведений (`zira`, `qahva`, `merve`, `rohat`,
`brunch`, `saffron`, `oshkhona`, `tea-house`, `rooftop-dinner`,
`chaihona-somon`, `siyoma-dessert`, `samarqand-cafe`, `navruz-breakfast`,
`green-bowl`, `dushanbe-bistro`) переведены в `status='archived'` +

Архив, а не удаление: на этих заведениях висит 21 визит, отзывы,
избранное, активации и QR-коды — история тестов приложения, по которой
считались статусы и выплаты.

update public.venues set status='active', deleted_at=null
 where slug in ('zira','qahva','merve','rohat','brunch','saffron',

                'siyoma-dessert','samarqand-cafe','navruz-breakfast',
                'green-bowl','dushanbe-bistro');

Код каталога лежит в `offers.catalog_code` — акций в документе шестьдесят,
заведено десять, и когда заведение попросит «включите K-13», найти её надо
по коду, а не по совпадению заголовка.

Шестой тип, `fixed` (скидка фиксированной суммой), ни одной акцией здесь
не представлен: в каталоге его нет. Все «фиксированные» позиции там —
это фикс-*цена* набора, то есть `combo`. Тип поддержан схемой и покрыт
тестами; заводить под него акцию, которой в каталоге нет, значило бы
выдумывать.

Пороги в сомони («чек от 1,5× СЧ») не проставлены: средний чек обоих
заведений неизвестен, документ сам оставляет его на этап настройки.
Даты начала и конца пустые — срок кампании проставляет админ при
одобрении.

**Восемь из десяти работают не круглые сутки.** Это замысел каталога, а не
недоделка: −25% в час, когда зал всё равно пустой, и −25% круглосуточно —
разные вещи. Гость видит акцию только в её окно, `check_promotion_limits`
отвечает `PROMO_OUTSIDE_HOURS` или `PROMO_WRONG_DAY` в остальное время.
Постоянно доступны только K-22 и Z-22.

Вернуть в черновики:

```sql
update public.offers set status='draft'
 where catalog_code is not null and deleted_at is null;
```

Обычный путь акции — через модерацию:

```sql
-- заведение отправляет на проверку
select public.merchant_set_promotion_status('<id>', 'moderation');
-- админ одобряет
select public.admin_review_promotion('<id>', true, 'согласовано с заведением');
```

## 9. Расхождение репозиториев ⚠️

`supabase/migrations/` в этом репозитории **не описывает базу целиком.**

В проекте `lfudcjwkyctodeqaommv` на момент этой ветки было 40 миграций,
которых здесь нет: их накатывает репозиторий внутренней админки
(`bakhtovar/Blast-Internal-Admin`) прямо в ту же базу. Оттуда все
41 функция `admin_*`.

Практическое следствие: **`supabase db push` из этого репозитория не
работает.** CLI видит чужие миграции и требует пометить их как
`reverted` — этого делать нельзя, история общая. Миграции этой ветки
применены через MCP `apply_migration`; файлы в `supabase/migrations/`
остаются записью изменения, а не источником для `db push`.

Пересоздание базы из одних лишь этих миграций даст базу без админки.
