# Google Play: что готово и что мешает

Проверка 11 сентября 2026. Смотрел не по памяти: собрал релизный бандл,
распаковал его и прочитал, чем он подписан, какие разрешения туда попали и
что лежит внутри.

Собирается и запускается: `flutter build appbundle --release` проходит,
`app-release.aab` — 78,5 МБ, три ABI внутри (arm64-v8a, armeabi-v7a,
x86_64). Play раздаёт под устройство только нужную, так что гость скачает
около трети.

Целевой API 36, минимальный 24 — требованиям Play соответствует.

## Блокеры: без этого не примут

### 1. Бандл подписан отладочным ключом

```
Owner: CN=Android Debug, O=Android, C=US
SHA1:  50:BA:2E:5D:38:5F:A2:A8:21:25:13:AA:52:C2:4B:98:E9:70:9D:F5
```

Play такую загрузку отклоняет сразу: «You uploaded an APK or Android App
Bundle that was signed in debug mode». В `build.gradle.kts` стояла заглушка
от `flutter create` — `signingConfig = signingConfigs.getByName("debug")` с
комментарием TODO.

**Сделано:** gradle теперь читает `android/key.properties` и подписывает
релиз настоящим ключом; пока файла нет, остаётся отладочный — чтобы
`flutter run --release` на своём телефоне продолжал работать.

**За вами — сам ключ.** Создать один раз и не терять: потеряете — не
сможете обновлять приложение.

```bash
keytool -genkey -v -keystore ~/blastpay-upload.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

Затем `android/key.properties` (он в .gitignore):

```properties
storeFile=/Users/<вы>/blastpay-upload.jks
storePassword=<пароль хранилища>
keyAlias=upload
keyPassword=<пароль ключа>
```

Проверить, что подпись сменилась:

```bash
keytool -printcert -jarfile build/app/outputs/bundle/release/app-release.aab | head -3
```

В строке Owner не должно быть «Android Debug».

### 2. Политика конфиденциальности

Play требует ссылку в двух местах: карточка приложения и форма Data safety.

**Снято 13 сентября:** сайт поднят, `https://blastpay.tj/privacy` отвечает.

### 2а. Апекс-домен перенаправляет на www — это ломает диплинки

```
https://blastpay.tj/.well-known/apple-app-site-association
  → 301 https://www.blastpay.tj//.well-known/...   (200)
```

Перенаправляется весь апекс, причём с лишним слешем в адресе. Ни Apple, ни
Google при проверке привязки по перенаправлениям не ходят — им нужен
ответ 200 с самого домена. Следствия:

- **iOS: universal links не работают уже сейчас**, в собранном приложении.
  В `Runner.entitlements` стоит `applinks:blastpay.tj`, а проверить его iOS
  не может. Наклейка с QR открывает браузер вместо экрана активации.
- **Android:** то же самое ждёт `assetlinks.json`, как только он появится.

Править в коде нечего: оба домена привязаны к воркеру
(`wrangler.jsonc`, `custom_domain`), перенаправления в нём нет — значит это
правило в панели Cloudflare (Rules → Redirects), а они срабатывают раньше
воркера.

**За вами:** в Cloudflare снять правило перенаправления с апекса (воркер уже
привязан к обоим именам и отдаст сайт сам) либо исключить из него
`/.well-known/*`. Проверка после правки:

```bash
curl -sI https://blastpay.tj/.well-known/apple-app-site-association | head -1
```

Ожидается `HTTP/2 200` без единого перенаправления.

### 3. Формы в Play Console

- **Data safety** — аналог App Privacy. Те же девять типов данных, что в
  `docs/app-store-connect-forms.md`; трекинга нет, данные привязаны к
  аккаунту, передаются по HTTPS, удаляются вместе с аккаунтом.
- **Content rating** — анкета IARC. Ответы те же: алкоголь упоминается
  («Винный вечер»), пользовательский контент есть, рекламы нет.
- **Target audience** — 13+ (не детское приложение, не Families).
- **Ads** — «нет рекламы».
- **App access** — вход обязателен, поэтому нужно дать проверяющим учётные
  данные. Подходит тот же демо-аккаунт: `review@blastpay.tj`, вход по
  паролю, очередь его не держит.
- **Government apps / Financial features** — приложение не финансовое: оплату
  проводит банк в своём приложении, денег Blast не принимает и не хранит.
  Отвечать «no financial features», но быть готовым объяснить название.

короткое описание до 80 знаков, полное до 4000.

## Сделано этой проверкой

- **`INTERNET` объявлен в основном манифесте.** Он был только в debug- и
  profile-манифестах, а в release приезжал транзитивно из
  `google_sign_in_android`. Уберём Google-вход — и сборка уедет в Play без
  сети, молча: ни одной ошибки сборки при этом не будет.
- **Подпись релиза вынесена в `key.properties`** с откатом на отладочный
  ключ, пока файла нет.

## Сделано 13 сентября

Проверено на собранном бандле: строки манифеста и слои иконки читались
внутри готового `app-release.aab`, а не только в исходниках.

- **`make aab`.** Та же ловушка, что описана у `make ipa`, только тише:
  `flutter build appbundle` без `--dart-define` собирается молча, а
  `SUPABASE_URL` и ключ внутри оказываются пустыми строками — в Play уехал
  бы бандл с белым экраном. Таргет подставляет окружение из `.env.local`,
  предупреждает про отсутствующий `key.properties` и в конце печатает
  владельца сертификата, которым подписан бандл.
- **Adaptive icon** — `tool/make_android_icons.py` собирает слои из
  иконки App Store, чтобы две платформы не разъезжались. Логотип «BLAST» —
  полоса 6,3 : 1, в гарантированную окружность 66dp такая влезает шириной
  до 65dp; взято 60dp. Заодно слой monochrome для Android 13+.
- **App Links в манифесте** — `/q/` и `/venue/` на обоих именах домена,
  пути те же, что в `apple-app-site-association`.
- **Разбор входящих ссылок** — `lib/core/web_links.dart`. Флаг
  `flutter_deeplinking_enabled` **намеренно не включён**: он отдаёт
  go_router вообще все ссылки, включая `io.supabase.blast://login-callback`
  с токеном возврата OAuth, и увёл бы человека с середины входа. Слушаем
  только https со своего домена, callback достаётся supabase_flutter.
- **`POST_NOTIFICATIONS` объявлен явно.** В бандл он приезжал транзитивно
  из `flutter_local_notifications` — ровно так же, как когда-то приезжал
  `INTERNET`.
- **`tool/make_assetlinks.sh`** — соберёт файл привязки, когда появится
  ключ. Напоминает про второй отпечаток, от Play App Signing: именно его
  чаще всего забывают, и тогда ссылка работает у разработчика и открывает
  браузер у всех остальных.

Разрешения в собранном бандле, для формы Play: `INTERNET`, `CAMERA`,
`ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, `ACCESS_NETWORK_STATE`,
`POST_NOTIFICATIONS`, `VIBRATE`, `USE_BIOMETRIC`, `USE_FINGERPRINT`,
`BIND_JOB_SERVICE`. Фоновой геолокации нет — про неё Play спрашивает
отдельно и требует видео-обоснование.

## Порядок

0. **Завести аккаунт Play Console** — 25 $ и проверка личности. У личных
   аккаунтов перед продакшеном требуется закрытое тестирование: около
   двенадцати участников, непрерывно четырнадцать дней. Точные цифры
   меняются, смотреть в Консоли. Это самый долгий пункт и единственный,
   который нельзя ускорить, — начинать с него, остальное идёт параллельно.
1. Создать ключ, положить `key.properties`, пересобрать через `make aab`,
   убедиться по строке «Подписан:» в конце, что владелец не «Android Debug».
2. ~~Поднять сайт с политикой.~~ Сделано. Осталось снять перенаправление
   с апекса — пункт 2а, без него не заработают диплинки ни на одной из
   платформ.
3. Создать приложение в Play Console, загрузить бандл в internal testing —
   формы там заполняются по ходу.
4. Зарегистрировать SHA-1 обоих ключей в Google Cloud, иначе Google-вход у
   первых же тестировщиков не сработает.
5. Сгенерировать `assetlinks.json` (`tool/make_assetlinks.sh`) отпечатками
   обоих ключей и выложить на домен. Второй отпечаток — от Play App
   Signing — появится только после шага 3.
6. Решить, что делать с пушами на Android: либо FCM, либо спрятать
   переключатели на этой платформе, чтобы не обещать то, чего нет.
